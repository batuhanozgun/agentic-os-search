## U13-B disposition — Q07d3

**Original criterion:** selected repository/package/lock inputs → rule/advisory identity and freshness → scan/match/exclusions → result/missingness → CLI exit/report → actual CI/release decision and update/retry. A coherent useful chain and material coverage/freshness/error counterparts are now explained.

The local scanner uses finite in-code indicators; the separate reporter validates source metadata and optionally URL status. Neither consumes the other's output to update scanner rules. CI/watch additionally perform separate npm signature/advisory checks. Actual scanner findings can stop the followed jobs and release verification; the finite matcher is not the entirety of their security controls.

Coverage depends on the default module-relative root, explicit filenames/directories and installed-package traversal. Hidden/symlinked or nested package layouts can fall outside the payload walker, while lockfile version detection remains possible. Home/system-temp targets are opt-in and absent from the actual followed commands. A nonexistent root can return zero files/findings; some content/hash read failures become empty strings, unlike traversal errors that may exit2. The selected count is not a successful-read count. Defensive deny exemptions follow repeated values throughout raw text, not only their structural field positions. All countercases retain their conditions and useful positive controls.

Advisory metadata can be ready while refresh fails or was not requested; detailed warnings remain. A coarse proposed Linear summary uses ready to say sources are current. Strict-refresh is an optional CLI exit policy, not a rewritten ready field, and is not enabled by the watch. URL reachability does not establish content recency or rule adoption; GET fallback timestamps and exhausted redirects have additional source-level limits. In watch, an early failure can prevent later report generation despite always-upload. No target execution or E10 occurred.
