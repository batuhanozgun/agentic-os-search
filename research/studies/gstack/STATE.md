## Current strongest cross-subsystem findings

### C1 — gstack is a qualification-driven work system
**Status:** strong working system hypothesis; cross-system synthesis still required.

```text
Planning/spec        → qualifies intent before admission
Review/ship          → qualifies implementation before delivery
Browser/runtime      → qualifies capability, effect and evidence
Investigate          → qualifies causal explanation before corrective mutation
Memory/context       → qualifies prior information before reuse
Multi-agent          → qualifies delegation, completion and child evidence
Guarded/security     → qualifies effect authority and security claims
Host portability     → qualifies semantic/control fidelity on target runtime
Production feedback  → qualifies merge, deploy, live health and historical outcome
Testing/eval         → qualifies whether verification actually ran and what it proves
Self-development     → qualifies generated, installed, upgraded and released system state
```

### C2 — current standing matters more than ceremony history
Reviews, plans, refs, cached knowledge, child results, host renders, deploy state, eval runs and installations each have their own invalidation conditions. A named prior ceremony is not automatically current evidence.

### C3 — typed artifacts can become control inputs
Plans, reviews, decisions, checkpoints, learnings, child JSON, generated skill trees, deploy artifacts, eval manifests and version state alter later work. Their authority is consumer-, freshness- and runtime-specific.

### C4 — authority is resource-specific
User approval, delegated child scope, runtime capability, memory/brain policy, one-way doors, merge/rollback authority, repository ownership and version allocation are different relations.

### C5 — freshness is object-relative
Diff, plan, browser ref, checkpoint, learning, brain digest, child result, security report, host render, deployment, eval run, generated skill and running daemon become stale for different reasons.

### C6 — evidence diversity is not verification independence
Fresh same-family agents, Codex, deterministic tests, LLM judges, browser observation, security verifiers and production probes share different common causes/oracles. Agreement helps; it is not automatic independent replication.

### C7 — failure polarity is deliberately heterogeneous
Uncertainty may deny, ask, degrade, preserve old state, suppress a claim, continue with partial evidence, warn, allow explicit override or fail open to preserve availability.

### C8 — source→view fidelity is system-level and recursive
Observed examples include:

- template/resolver → generated skill;
- source tree → installed runtime assets;
- checkpoint → current repo;
- GBrain `stale-fallback` → planning context with stale label lost;
- child JSON → parent decision;
- security/deploy report → current live state;
- partial eval artifact → list/summary consumer;
- host docs → actual setup implementation;
- repository HEAD → setup/materialized install;
- VERSION → main-HEAD-oriented user upgrade.

### C9 — transition completion is not target-condition completion

```text
review ran       ≠ implementation qualified
merge completed  ≠ deploy completed
deploy completed ≠ application healthy
revert pushed    ≠ production restored
source HEAD moved ≠ installed runtime materialized
migration selected ≠ migration completed
```

### C10 — liveness is correctness
Parent/child waiting, process-group cleanup, update locks/heartbeats, merge queue polling, deploy waiting, daemon replacement and partial-effect reconciliation are correctness properties, not incidental operations.

### C11 — isolation must name the resource
Fresh context, model/provider, worktree, browser tab, filesystem, process group, local render tree, memory and host runtime are distinct isolation dimensions.

### C12 — support/verification is a ladder, not a boolean

```text
registered
< generated
< structurally valid
< installable
< runtime-capable
< workflow-executed
< failure-path exercised
< independently validated
```

### C13 — prevention, authority, detection and evidence are different control layers
A hook that can stop an action, a human approval requirement, a security finding and a verification report have different semantics and must not be collapsed into one “gate” concept.

### C14 — gstack evolves by converting repeated failures into stronger control surfaces
A recurring repository-evolution pattern is:

```text
prose / convention
→ concrete failure
→ named state distinction
→ reusable resolver/helper/CLI
→ structural invariant/scanner
→ behavioral/environment E2E
→ CI/release consequence when justified
```

This pattern is strong but incomplete; the pinned repo still contains explicit counterexamples and TODOs.

## Protected negative findings / cautions

1. Derived docs never override pinned source/tree.
2. First-party tests/evals are evidence, not independent external verification.
3. GBrain warm/stale distinction is lost in current planning preflight representation.
4. Eval partial/finalized standing is preserved in baseline/flake tooling but can be flattened by `eval-list` / `eval-summary` consumers.
5. Same-family fresh context and cross-model diversity are different independence notions.
6. Pair-agent own-only isolation is browser-tab-specific.
7. Investigate freeze is not a full filesystem sandbox and is host-specific.
8. `/careful` HIGH deny is session-scoped and explicitly not a universal policy boundary.
9. `/guard` does not make Bash filesystem mutations obey freeze's Edit/Write boundary.
10. Claude runtime interposition can degrade to prose self-policing on external hosts.
11. Host registry membership is not first-class runtime support evidence.
12. Non-Claude behavioral validation is sparse outside Codex; external-host generated output is not committed-byte-freshness checked.
13. CSO is not equivalent to professional pentesting or a live ship gate.
14. A green test lane is not positive verification when intended runtime/oracle skipped.
15. LLM-judge scores are calibration/model-dependent, not objective quality truth.
16. `REVERTED` does not prove production restoration.
17. Canary live health is not automatically exact-release identity proof.
18. Retro recommendations are informational feedback, not automatic Work admission or Actor obligation.
19. Update-check script crashes preserve `UNKNOWN`, but invalid/unreachable remote VERSION is currently cached as `UP_TO_DATE`; remote freshness was not established in that path.
20. Session-start updater can advance repository HEAD and emit update-completion markers even when `./setup -q` logs failure; targeted tests cover pull/lock behavior but not this completion-standing sequence.
21. Migration outer runners are version-window based; a migration that intentionally/default-skips can be passed permanently by the outer version marker. The repository itself tracks per-migration done/skipped state as unfinished work.
22. VERSION/release identity is not a tag-pinned immutable install contract at the pinned design; update-check uses main VERSION while upgrade installs main HEAD.
23. Version Gate intentionally fails open when queue-allocation infrastructure is unavailable.
24. Numeric version validity does not prove semantic bump-level correctness.
25. All conclusions remain pinned-revision conclusions; upstream is fast-moving.
