## Important non-collapse rule

Do **not** infer:

```text
Technical Work Environment ⊂ product/system Operating World
```

as a universal hierarchy.

ISO/NIST systems-engineering terminology distinguishes enabling systems used for life-cycle work from systems in the system-of-interest's operational environment. Development/test/support systems can therefore be outside the product's operating world.

The stronger project relation is sibling **roles/branches around focal Work**, not physical/object containment.

## Environment parent exclusion rule

Reject:
- `Environment = everything relevant`;
- `Environment = everything outside`;
- `Environment = Context`;
- `Environment = all tools/resources/constraints`.

The same concrete thing can participate in several grounds.

Examples:
- another person can affect operating conditions while identity/authority/accountability remain Actors semantics;
- a regulation can be an operating constraint while its text/version is Information and its authority involves Actors/control;
- a repository can be a support resource and contain Records;
- a CI/test system can be support environment for product Work and become the target/domain of maintenance Work.

Grounds are analytical problem lenses/roles, not mutually exclusive object types.
