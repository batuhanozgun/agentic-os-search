## Belge ekseni: `multiagent`

### Araştırmacı özeti

K1 (a role asks another role for something and gets the result back) works inside a single cloud session. It is only partly documented across sessions. I made no files and changed nothing.

(1) What exists. There are five ways to run several agents: subagents, agent view, agent teams, dynamic workflows and Projects.
- **Subagents:** Claude orchestrates turn by turn. Each subagent has its own context and returns a summary to whoever called it. A subagent Claude names can be messaged or resumed with SendMessage, and the answer goes back to the agent that asked. That is the closest built-in match for K1.
- **Agent teams:** a lead plus teammates who message each other directly and share a task list. They are experimental and scoped to one session.
- **Dynamic workflows:** a script holds the plan and runs many subagents, keeping intermediate results in script variables. They suit big fan-out jobs but take no user input while running.
- **Projects:** a coordinator conversation in claude.ai/code starts parallel cloud sessions called threads. Each thread reports back to the coordinator when it finishes, and project memory and instructions carry context across threads.
- **Cross-session messaging:** a local session reaches cloud sessions only while it is connected to Remote Control. Otherwise the message is one-way and cannot be answered.
- **Cloud-to-cloud messaging:** the Agent SDK reference says cloud sessions message each other with a server-side `send_message` tool. The create_session, get_session and list_events tools this session has are not documented on code.claude.com.

(2) Cloud vs local. The cloud docs say subagents work the same as locally, and the repo's `.claude/agents/` loads automatically. Agent teams can be turned on in a cloud environment by setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Workflow results are saved with the cloud conversation. Projects run only in claude.ai/code, the desktop app and mobile; they are a public beta on Pro and Max, not yet on Team or Enterprise, and rolling out gradually. Agent view is local only: its sessions run on your machine under a supervisor process (agent-view.md). Files in the user-level `~/.claude/agents/` do not reach cloud sessions.

(3) Limits.
- Subagents can nest up to 3 layers by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`). Up to 20 can run at once (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), with no cap on the total per session.
- Workflows run up to 16 agents at once by default, fewer in a CPU-limited container, and at most 1,000 per run.
- Agent teams allow one team per session, no nested teams, and `/resume` does not bring teammates back. The team config is deleted when the session ends.
- In the cloud, a session's VM is reclaimed after inactivity. Reopening restores the conversation, but subagents and shell commands still running at that moment are not restored.
- Project threads can lose uncommitted changes, and the docs say to commit and push work in progress. There is a limit of 200 new threads per day.

(4) Roles. A role is a Markdown file in `.claude/agents/` with YAML frontmatter; only `name` and `description` are required. It is project-scoped, meant to be committed to the repo, and loaded automatically by fresh cloud sessions and Project threads. A `memory: project` field gives each role a persistent memory folder in the repo (`.claude/agent-memory/<name>/`).

Net answer: one cloud session with repo-defined subagents covers K1 while it lives. Nothing that is running survives the VM being reclaimed, so role state and the work queue have to live in committed repo files. For multi-session continuity the documented path is Projects, which depends on plan and rollout. Sibling cloud sessions via create_session and send_message are only partly documented.

Two notes come from this session's own tool descriptions, not from the docs. The ListAgents tool says a cloud session "receives your message but cannot message any session back yet". The create_session tool says a session that finishes cleanly "does not report back", so results must be pulled with get_session or list_events. That would weaken K1 across sibling cloud sessions.

### Açık sorular

- The Claude Code Remote MCP tools in this session (create_session, send_message, get_session, list_events, interrupt_session, archive_session) are not documented on code.claude.com. The only documentation is the SDK reference's mention of a server-side send_message. Their limits, costs and reply semantics come only from the tool descriptions. For example, ListAgents says a cloud session "cannot message any session back yet", and create_session says a session that finishes cleanly "does not report back".
- Is this cloud session connected to Remote Control? That decides whether SendMessage and /list-agents can reach other cloud sessions with a reply address.
- Does the user's account have Projects (public beta, Pro and Max only, gradual rollout, not Team or Enterprise)? Can the current session be turned into a Project with 'Continue as a project'?
- The docs do not say how an in-process agent team is viewed or steered in the claude.ai/code web UI. The docs describe a terminal agent panel.
- Subagent project memory (.claude/agent-memory/) and the agent-team task list (~/.claude/tasks/) are written to local disk. In an ephemeral cloud VM they persist only if committed and pushed; the task list is under ~/.claude and would not be in the repo. The docs do not address this for cloud.
- The docs do not say whether fork mode (background subagents by default) is on in cloud sessions, or how background-subagent permission prompts appear in the web UI.

## Belge ekseni: `continuation`

### Araştırmacı özeti

Verdict for K2 (keeping the design work moving without the user typing "devam"): yes, this cloud environment has what's needed, but no single mechanism does it alone. It takes three layers, and the docs mark two limits clearly.

(1) Inside one session, the documented engine is /goal. It is a session-scoped Stop hook that uses a Haiku judge. After each turn the judge checks the condition; if it isn't met, the judge starts another turn instead of handing control back. The user types it once (it is a built-in command, not a tool the agent can call). For unattended turns the session should be in Auto mode. /goal stops when:
- the condition is met;
- the judge rules it impossible;
- there has been no tool use for several turns in a row;
- a turn fails on an error the user has to fix;
- the user runs /goal clear.

Background subagents and Workflow runs fit inside this, because each finished result is delivered as a new turn. Without /goal, even Auto mode ends the turn "when it judges the work done". A Stop hook committed to the repo's .claude/settings.json works the same way in a single-repo cloud session, capped at 8 consecutive continuations. Writing that file is not allowed right now.

(2) The limit: everything in-session is tied to the session's VM. This covers /loop, ScheduleWakeup, CronCreate, Monitor, background subagents and background shells. Cloud sessions "stop after a period of inactivity and the session's VM is reclaimed", and on reopen "Background work ... such as subagents and shell commands, isn't restored". Cron tasks fire "only ... while Claude Code is running and idle". Recurring ones expire after 7 days. The /loop scheduling table lists them as running on "Your machine" with an open session required. The inactivity timeout is not documented.

(3) For work that survives idle expiry, the docs cover two things:
- Routines: cloud; schedule (minimum 1 hour), API or GitHub triggers; each run is a new, fully autonomous session with no permission prompts; daily run cap; research preview.
- Projects: a coordinator conversation plus parallel cloud threads with shared memory; threads run in Auto mode and continue on their own after a usage limit resets. This fits the DevOS multi-role idea best, but it is a public beta on Pro/Max that is still rolling out.

Mapping to the main agent's tools:
- The send_later / create_trigger tools (including "fire into THIS session") are durable schedulers the agent can use without the user. The public docs only describe routine runs as new sessions, so the "fire into this session" behaviour is not documented.
- /schedule itself is unavailable inside a cloud session.
- Channels effectively need a local launch with --channels, so they don't apply here.
- An outside driver (the user's machine or CI) can push messages into this session with `claude -p "..." --cloud <session-id>`.

Blockers for unattended cloud runs:
- Bypass mode is not available in cloud; Auto mode requires the org to allow it and the model to support it.
- MCP connector approvals wait on the user, and the session can expire while waiting.
- Usage and rate limits are shared across the account and pause /goal; routine-started threads don't wait for a reset.
- Uncommitted work can be lost when a sandbox is replaced, so work in progress should be committed and pushed often. That matches the existing Stop hook and the rule to push only to claude/ branches.

## Belge ekseni: `cloud`

### Araştırmacı özeti

Verdict for this dimension: yes, with caveats. This cloud environment can run a long, multi-session DevOS process, but no single cloud session is a durable, always-on process. The design has to treat git and repo files as the only durable state.

What the docs establish for cloud sessions (claude.ai/code):
(1) A session keeps running after the user disconnects, but it idles once the current task finishes. Something has to start the next turn: a user message, a CLI follow-up (`claude -p ... --cloud <id>`), a routine, or a project coordinator.
(2) After an undocumented period of inactivity the VM is reclaimed. Reopening restores the conversation, but running subagents and shell commands are lost. Waiting on an MCP connector approval counts as inactive.
(3) Uncommitted changes can be lost when a sandbox can't be resumed. The docs say to commit and push work in progress.
(4) Only repo-committed config reaches a cloud session: CLAUDE.md, .claude/agents, skills, rules, and .claude/settings.json (settings.json only in single-repo sessions). User ~/.claude files do not.
(5) Only Accept edits, Plan and Auto modes exist; there is no Bypass mode. Unattended tool use without prompts needs Auto mode, which appears only if the organization allows it and the model supports it.
(6) Projects is the documented product feature for "work spans many tasks over days or weeks". A coordinator conversation starts parallel cloud threads in auto mode, keeps project memory, compacts automatically and waits through usage-limit resets. It is public beta on Pro and Max only (not Team or Enterprise), is rolling out gradually, and is not available through the CLI.

Git: the GitHub proxy lets `git push` go only to the session's current working branch. The flow is claude/-prefixed branches plus a PR, then a merge to main. That changes the earlier ChatGPT practice of committing directly to main.

Instructions gap observed in this checkout: the repo root has AGENT.md (singular) and no CLAUDE.md, no AGENTS.md and no .claude/ directory. The docs name only CLAUDE.md, .claude/CLAUDE.md, AGENTS.md and .claude/AGENTS.md. So AGENT.md is not documented as auto-loaded, and the project's agent instructions are currently not loaded automatically. The documented fix is a CLAUDE.md containing an `@AGENT.md` import, or renaming the file to AGENTS.md.

Auto memory lives in ~/.claude/projects/<project>/memory/ on the VM and is "not shared across machines or cloud environments", so it is not a reliable cross-session store here. Repo files (or project memory in Projects) should hold DevOS state.

Compaction: it runs automatically. Cloud sessions set CLAUDE_AUTOCOMPACT_PCT_OVERRIDE, so it triggers earlier than in the full window; this variable is observed set in this container. Compaction drops full tool outputs and reasoning, so plans and handoffs must be persisted to files.

Usage limits are shared with all of the account's Claude usage. Parallel fan-out uses them proportionally faster.
