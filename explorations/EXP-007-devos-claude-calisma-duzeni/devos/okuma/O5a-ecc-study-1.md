## 3. ECC'nin mimarisi (study'ye göre)

**Yüzeyler (U01-A, STRUCTURE):** `package.json` altı binary tanımlar: `ecc`/`ecc-universal` → `scripts/ecc.js` (komutu ayrı Node script'ine yönlendiren dispatcher; "Calling the dispatcher an end-to-end orchestrator would overstate what this file proves"), `ecc-install` → `install-apply.js`, `ecc-control-pane`, `ecc-memory-mcp` → `memory-mcp.mjs`, `ecc-plan-canvas`. Ayrıca Rust `ecc2/` ("alpha control-plane scaffold"), `workflows/` (native Workflow pilotu), Python `src/llm`, 18 host klasörü (`.claude`, `.claude-plugin`, `.codex`, `.cursor`, `.kiro`, `.opencode`, `.pi`…). npm `files` listesi `workflows/` ve `ecc2/`'yi içermiyor: dağıtım kanalı yüzeye göre değişiyor [kaynak diyor].

**Yapılandırma boyutları ayrı:** "Install profile, hook profile, plugin enablement, host hook trust and source/runtime version are distinct. For example S08's `minimal` install profile omits `hooks-runtime`; S18 passes `minimal,standard,strict` to the SessionStart runner" (STRUCTURE).

**ECC ne veriyor, ne dışarıda kalıyor (CORE §2 tablosu, özet):**

| Sağlanan sorumluluk | ECC'deki mekanizma | Dışarıda kalan koşul |
|---|---|---|
| Yöntem ve uzman rehberliği | skill, command, rule, agent, aşamalı plan/review prosedürleri | Bir host/ajan bunları bulmalı, yorumlamalı, izlemeli; imzalar insanda |
| Erişilebilirlik ve bakım | native plugin, manifest-tabanlı kurulum, paylaşılan settings yönetimi, legacy sync | Seçilen dağıtım ve host doğru yükü yüklemeli |
| İş temsili ve alım | kartlar, zamanlamalar, remote istekler, handoff mesajları, şablonlar | "A record is not itself an allocated process or accepted task" |
| Yürütme ve denetim | worktree/tmux yardımcısı, Rust ECC2, Python sağlayıcı döngüsü | Birbirinin yerine geçmez; yetki ve ömür seçime bağlı |
| Bilgi ve yeniden kullanım | Vault, gözlem/instinct, oturum özetleri, graph recall, transcript replay | Kapsam, kanıt statüsü, gerçek alıcı ve bağlama giren şey ayrı |
| Geri bildirim, gözlem, nitelendirme | Plan Canvas, native review, metrikler, evaluator'lar, guard'lar, release | Her kontrol belirli bir nesneyi ölçer; sonucu doğru tüketiciye gitmeli |

**Dört bağlantı türü (CORE §9):** (1) dar sözleşmeyle gerçek ve yararlı (release arşivinin yayına taşınması); (2) kurulu ama dönüştürülmüş ya da tutarsız seçilmiş (kümülatif maliyetin toplanması); (3) bilinçli olarak aktör aracılı (plan onayı, Canvas geri bildirimi, TDD kanıt yargısı, PR kararı); (4) izlenen yolda kurulmamış (governance log → DB; terfi edilen Rust adayı → worker). DevOS için pratik anlamı: bir mekanizmayı "var" diye sayamazsın. Hangi türde olduğunu, yani eklemin kodla mı, aktörle mi kurulduğunu, yoksa hiç kurulmadığını yazmalısın [çıkarım].

**Kullanıcı görevinin ECC içinde yolculuğu (CORE §4)** "analytical composition of available routes, not a claim that one default command automatically performs all stages". Plan komutu inline çalışır ve koda geçmeden ayrı onay ister; "Writing a plan and marking a milestone in-progress can therefore precede permission to code". Uygulama TDD talimatına bağlı, ama "Neither written TDD guidance nor a running process is a task-quality certificate". Review'da "A script-level `APPROVE` is not authenticated user consent". Öğrenme ve devirde: "They do not automatically turn this task's output into accepted general knowledge or a proven improvement." Sonuç cümlesi: "A synthesis that removes the actor-owned steps would invent automation; one that ignores the real software would understate ECC."

**Aile haritası (U07-A):** Hook ağırlıklı ilk turlar bütün sistemi temsil etmiyordu: "the governance logger is not all human review, the Node skill evaluator is not all evaluation, and the tmux worker is not all session control." Harita her kök klasöre bir statü verdi; yinelemeli semantik kapsam tamamlanmadı ("P1 remains PARTIAL").

Seçim zinciri: "named request → component/module resolution → target/dependency filtering → adapter operation plan". Ör. `skill:tdd-workflow` bileşeni `workflow-quality` modülüne gider. Apply motoru Markdown linklerini yeniden yazar, MCP'yi süzer, JSON birleştirir, Claude settings'i ayrı yönetilen hook yolundan geçirir; içerik özetleri alır; `plannedOperations/operations/skippedOperations` ayrı tutulur. Çok-host kurulum sıralı: hata olursa `partial` ve `retryHarnesses` döner, global geri alma yok. Guided kurulumda "Claude and Codex use native-plugin reconciliation; Kimi uses a managed-project plan" (N02 §6). Sahiplik (N03): kayıtlı olmayan mevcut dosya atlanır, "Successful batch result does not imply ownership of every requested destination"; `installedAt` yazımdan önce oluşabilir; state yazıcı `writeFileSync` kullanır, tmp/rename/fsync yok; checkpoint "not an effect journal in which every row means done".
- **Kanıt:** E01 — `check-plugin-cache.js` yalnız `skills`, `mcpServers`, `interface.composerIcon`, `interface.logo` alanlarını topluyor, `hooks` alanını toplamıyor. C0 tümü mevcut → 0; C1 hook dosyası yok → 0 ("All cached manifest references resolve."); C2 MCP yok → 1. Doğrulamam: 2.2.2'de `collectManifestRefs` (satır 143–162) hâlâ `hooks` alanını toplamıyor, manifestte ise `"hooks": "./hooks/codex-hooks.json"` var [gözledim]. Ayrıca N02 §7: "installing that skill alone does not provide the `ecc memory` runtime". Model olarak da: "source available ≠ selected ≠ materialized ≠ recorded/visible ≠ admitted by host ≠ used effectively".
- **DevOS:** ECC installer'ını çalıştırma; alma. Bulutta `$HOME` hedefli ve buluta ait olmayan bir süreç olur; hedefi olan `claude-project` de study'de incelenmedi. ### M2. İş kaydı: work-item kartları, claim ve taşıma (N04, E02)
- **Sorun:** İşin kimde olduğu, durumu ve oturumla ilişkisi.
- **Nasıl işler:** `scripts/work-items.js` → şema doğrulama → SQLite upsert (`state.db`, tablolar: sessions, work_items `session_id` FK `ON DELETE SET NULL`, skill runs, decisions). Claim yardımcısı (`control-pane/work-item-mutations.js`): id verilmezse son güncellenmiş 100 kart istenir; sahipli ve terminal kartlar süzülür; kalanlar bu pencere içinde önceliğe göre sıralanır. ### M16. Native review pilotu (N19, E08)
- **Nasıl işler:** `workflows/orch-review.workflow.js` yalnız review ve doğrulama segmenti. `/orch-review` yerel diff ya da PR numarası/URL alır (kabuk karakterlerini reddeder), ama gh'ye yalnız numara geçer (`--repo` yok). Boyutlar: quality her zaman, dil, güvenlik (sözcük tabanlı regex). Birleştirme anahtarı dosya + normalize edilmiş kanıt metni; ilk bulgunun alanları kalır, yalnız en ağır şiddet alınır. Koruma kuralları: reviewer null/reddettiyse → boyut başarısız → CHANGES_REQUESTED/incomplete; doğrulayıcı null/hata → doğrulanmamış bloklayıcı; false ve güven <0.8 → belirsiz bloklayıcı; false ve ≥0.8 → danışma; true → bloklayıcı (güven 0.2 bile "confirmed" sayılıyor). Reviewer prompt'u: "Only report issues you are >80% sure are real problems. For any CRITICAL or HIGH finding you MUST supply concrete `evidence` and a `proof` of impact; if you cannot, demote it or drop it. Returning zero findings with verdict APPROVE is an acceptable and expected outcome for clean diffs." Doğrulayıcı prompt'u: "You are an independent skeptic... Set isReal=false ONLY if you can affirmatively demonstrate from the diff that the finding is a false positive, and report a high `confidence` (>= 0.8)... Uncertainty must never clear a blocker." Her iki prompt diff'i "untrusted input" olarak işaretler.
- **Kanıt:** E08 (uyarlanmış tek koşu, 18 senaryo, 38 yanıt şemaya uygun; ham kaydın SHA-256'sını doğruladım): önce MEDIUM sonra CRITICAL gelince tek CRITICAL bulgu kalıyor ama kanıt (proof) düşüyor, doğrulayıcı reddediyor → APPROVE; ters sırada → CHANGES_REQUESTED. Reviewer'ın CHANGES_REQUESTED + boş bulgusu → APPROVE. Diff olmayan metin kabul ediliyor. Boş diff → ajan çağrısından önce hata. Dış onay kapıları (plan, commit) prosedürde: "Returning APPROVE from it is therefore not user consent to commit."
- **DevOS:** **Uyarlayarak al, aş.** DevOS'un bağımsız gözden geçiren + doğrulayıcı rolü için en somut hazır şablon. Aşma: birleştirmede en güçlü kanıtı taşı; incelenen commit/diff özetini sonuca bağla; reviewer'ın kendi hükmünü de raporla; "confirmed" sayacını güvenle ayır. **Yargım (O-16'ya göre "örneğin üstüne kur"):**
1. "ECC'nin tamamı" tek kurulabilir sistem değil. Claude Code bulutu için anlamlı "bütün", ECC'nin Claude'a dönük varlık katmanıdır: skills, agents, commands, rules, hooks. Bu katman sabit pin ile, **eksiksiz** ve değiştirilmeden bir satıcı dizinine alınıp DevOS'un tabanı yapılabilir. Seçip kopyalamak (O5'in 10–15 bileşen önerisi) örneğin altında kalır ve pin yükseltmesini zorlaştırır [çıkarım]. Katalogun tamamını bağlama yüklemenin maliyeti (O5'in 107 KB ölçümü) ve Claude'un bunu nasıl budadığı O5c, O5d ve O11'in doğrulayacağı ayrı bir soru.
2. Bulut ve repo uyarlaması ayrı bir overlay katmanı olmalı: giriş noktası izin listesi, veri kökleri, devre dışı bırakılan buluta uygun olmayan hook'lar, profil seçimi. Her overlay değişikliği "hangi ECC dosyasının hangi satırını neden değiştirdi" kaydıyla tutulmalı (N03'teki sahiplik dersi).
3. ECC'nin kontrol katmanları (ECC2, control-pane, Plan Canvas, remote/scheduler/backlog/template, observer) alınmamalı. Study'nin kendi bulguları bunların ya bulutla uyuşmadığını ya da sahiplik/kabul boşlukları taşıdığını gösteriyor.
4. DevOS'un kendi katmanı ECC'yi aşmalı. ECC'nin boş bıraktığı ya da zayıf kurduğu her yer DevOS'un tasarım gereksinimi olur: deneme kimliği ve eski yazıcıyı reddetme (N15); tetik tekrarı kimliği (N20); revizyona bağlı onay (N12, N19); süreç çıkışından ayrı kabul (N05); kanıtı koruyan birleştirme (N19); gerçek tüketicide test (N16, N25); önceden kayıtlı ölçütle değişiklik terfisi (N08, N17); kısmi etkiyi kaydeden kurtarma (N20–N23); soğuk başlatma testi (METHOD-CASE); dar yama ile yayın (§6).
5. Bu yargı study'nin bu yarısına dayanıyor. Bulutta hangi ECC varlığının gerçekten yüklenip etkili olduğu hiç ölçülmedi. İlk DevOS adımlarından biri bir duman testi olmalı: pin'lenmiş katalog repo'da → yeni bulut oturumu → skill/agent/command keşfi, hook tetiklenmesi ve additionalContext'in modele ulaşması kayda geçer.
